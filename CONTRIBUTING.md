# Contributing Guide

## 1. Основные правила

* `develop` — основная ветка разработки и интеграции.
* `master` — стабильная ветка проекта и официальных релизов.
* Прямой push в `develop` и `master` запрещён.
* Любые изменения вносятся через Pull Request.
* Один PR должен решать одну логическую задачу.
* Перед созданием PR необходимо проверить изменения локально.
* CI должен проходить успешно перед merge.
* Изменения в архитектуре и интерфейсах должны быть отражены в документации при необходимости.
* Рабочее состояние существующего функционала не должно ломаться без явной причины и описания в PR.

---

## 2. Ветки

### `master`

Стабильная ветка проекта.

В `master` находятся версии, которые прошли необходимое тестирование и могут использоваться как стабильная версия `stingray_core`.

Изменения напрямую в `master` не вносятся.

### `develop`

Основная ветка разработки.

Все завершённые изменения после code review и успешного CI интегрируются в `develop`.

`develop` используется для:

* интеграции ROS 2 пакетов;
* проверки взаимодействия компонентов;
* подготовки изменений для аппаратного тестирования;
* подготовки следующих релизов.

`develop` может содержать изменения, которые ещё не вошли в стабильный релиз.

## 3. Feature branches

Работа над задачами выполняется в отдельных ветках, создаваемых от `develop`.

Формат:

```text
<type>/<description>
```

Допустимые типы:

* `feature/` — новая функциональность
* `fix/` — исправление ошибки
* `refactor/` — изменение архитектуры без изменения поведения
* `test/` — добавление или изменение тестов
* `docs/` — документация
* `chore/` — технические изменения
* `ci/` — CI/CD и инфраструктура

Примеры:

```text
feature/dvl-localization
fix/imu-frame-id
refactor/communication-architecture
test/pressure-sensor
docs/development-guide
chore/update-docker
ci/add-ros-build
```

Если для задачи существует GitHub Issue, рекомендуется добавлять её номер:

```text
feature/123-dvl-localization
fix/145-imu-timeout
```

## 4. Commits

Используется формат Conventional Commits:

```text
<type>: <description>
```

Основные типы:

* `feat` — новая функциональность
* `fix` — исправление ошибки
* `refactor` — рефакторинг
* `test` — тесты
* `docs` — документация
* `chore` — технические изменения
* `build` — изменения системы сборки
* `ci` — изменения CI/CD

Примеры:

```text
feat: add DVL localization node
fix: handle DVL timeout
refactor: split communication modules
test: add pressure sensor tests
docs: update development guide
chore: update Docker dependencies
build: update CMake configuration
ci: add ROS 2 workspace build
```

Commit должен описывать конкретное логическое изменение.

---

## 5. Pull Request

Обычные PR создаются из рабочих веток в `develop`.

Для каждого PR необходимо использовать шаблон:

```text
.github/pull_request_template.md
```

PR должен:

1. решать конкретную задачу;
2. содержать описание изменений;
3. содержать способ проверки;
4. иметь ссылку на Issue, если она существует;
5. проходить обязательные проверки CI;
6. иметь необходимое количество approvals.

Не следует объединять в одном PR несвязанные изменения.

Например, изменение алгоритма DVL и массовое форматирование всего проекта должны находиться в разных PR.

---

## 6. Локальная проверка

Перед созданием PR необходимо проверить изменения локально.

Минимальная проверка должна включать сборку workspace:

```bash
colcon build
```

или соответствующий проектный скрипт, если он предусмотрен.

Для работы рекомендуется использовать предоставленный Docker/Dev Container:

```bash
./docker/build.sh
./docker/run.sh
```

После запуска контейнера рабочее пространство находится в:

```text
/stingray_core
```

ROS 2 Humble автоматически подключается при запуске контейнера.

---

## 7. CI

Каждый Pull Request проходит GitHub Actions CI.

Текущая CI-проверка включает:

1. checkout репозитория;
2. загрузку git submodules;
3. сборку Docker image;
4. сборку ROS 2 workspace через `colcon build`.

CI должен завершаться успешно перед merge.

На данный момент `clang-format` не является обязательной CI-проверкой. Форматирование кода будет вынесено в отдельное изменение.

## 8. Git Submodules

Проект использует git submodules для внешних зависимостей.

После клонирования репозитория необходимо выполнить:

```bash
git submodule update --init --recursive
```

При необходимости можно сразу клонировать репозиторий вместе с submodules:

```bash
git clone --recurse-submodules <repository-url>
```

Перед началом работы рекомендуется проверить состояние:

```bash
git submodule status
```

Изменения внутри submodule являются отдельными изменениями и не должны случайно попадать в PR основного репозитория.

Если требуется обновить версию submodule, это должно быть явно указано в описании PR.

---

## 9. ROS 2

Новые ROS 2 компоненты должны соответствовать существующей архитектуре проекта.

При добавлении или изменении ROS 2 package необходимо учитывать:

* структуру package;
* зависимости `package.xml`;
* зависимости `CMakeLists.txt`;
* ROS 2 interfaces;
* topic/service/action interfaces;
* QoS;
* `frame_id` и TF;
* timestamps;
* lifecycle nodes, если они используются компонентом;
* параметры ROS 2;
* обработку ошибок;
* корректное завершение node.

Изменения ROS 2 interfaces должны быть явно описаны в PR, поскольку они могут затронуть другие компоненты системы.

## 10. C++ Code Style

За основу используется Google C++ Style Guide с дополнительными правилами проекта.

Основные требования:

* `.cpp` для исходных файлов;
* `.hpp` для заголовочных файлов;
* `#pragma once` вместо include guards;
* отступ — 4 пробела;
* максимальная длина строки — 100 символов;
* функции и методы — `snake_case`;
* константы — `UPPER_CASE`;
* значения `enum` — `UPPER_CASE`;
* фигурные скобки используются всегда.

Форматирование выполняется с использованием `.clang-format`.

В VS Code рекомендуется включить форматирование при сохранении файла.

Подробные правила находятся в:

```text
docs/development/coding-style.md
```

## 11. Code Review

Для изменений требуется минимум один reviewer.

Reviewer проверяет:

* корректность;
* архитектуру;
* обработку ошибок;
* ROS 2 interfaces;
* QoS;
* TF;
* timestamps;
* производительность;
* тестируемость;
* читаемость;
* отсутствие очевидных регрессий;
* соответствие существующей архитектуре проекта.

Для изменений, затрагивающих аппаратное взаимодействие, дополнительно необходимо проверить:

* корректность работы с устройством;
* serial/UART/I2C/CAN интерфейсы;
* обработку timeout и ошибок соединения;
* поведение при потере устройства;
* безопасность команд управления.

---

## 12. Merge в `develop`

PR может быть объединён с `develop`, если:

* CI проходит успешно;
* все обязательные проверки пройдены;
* нет unresolved comments;
* получены необходимые approvals;
* изменения проверены автором;
* документация обновлена при необходимости;
* тесты добавлены или обновлены при необходимости.

После merge рабочая ветка удаляется.

---

## 13. Release

Когда набор изменений в `develop` считается готовым к выпуску, создаётся Release PR:

```text
develop → master
```

Перед объединением в `master` необходимо выполнить необходимое интеграционное и аппаратное тестирование.

После успешного тестирования изменения объединяются в `master` и создаётся Git tag:

```text
v0.1.0
v0.2.0
v1.0.0
```

`master` должна содержать только стабильные версии проекта.

---

## 14. Hotfix

Если критическая ошибка обнаружена в текущем релизе, hotfix создаётся от `master`:

```text
master
   ↓
fix/critical-issue
   ↓
master
```

После исправления hotfix также должен быть перенесён в `develop`, чтобы исправление не потерялось в следующей версии:

```text
master
   ↑
   │
hotfix
   │
   ↓
develop
```

## 15. Общий workflow

```text
                    ┌──────────────┐
                    │    Issue     │
                    └──────┬───────┘
                           ↓
                    ┌──────────────┐
                    │    Branch    │
                    └──────┬───────┘
                           ↓
                    ┌──────────────┐
                    │ Development  │
                    └──────┬───────┘
                           ↓
                         PR
                           ↓
                    ┌──────────────┐
                    │     CI       │
                    └──────┬───────┘
                           ↓
                    Code Review
                           ↓
                     ┌─────┴─────┐
                     │           │
                     ▼           ▼
                   Reject      Approve
                     │           │
                     │           ▼
                     │        develop
                     │           │
                     │           ▼
                     │   Integration Testing
                     │           │
                     │           ▼
                     │      Release PR
                     │           │
                     │           ▼
                     │         master
                     │           │
                     │           ▼
                     │       Git Tag
                     │
                     └──→ исправления
```

### Главный принцип

> **`develop` — то, что мы сейчас разрабатываем и интегрируем.**
>
> **`master` — то, что мы официально выпустили и готовы использовать как стабильную версию.**
