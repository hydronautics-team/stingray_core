# C++ Coding Style

## 1. Общие правила

В проекте используется **C++17** и за основу берётся Google C++ Style Guide с дополнительными правилами проекта.

Основные цели:

* единообразный код;
* читаемость;
* предсказуемая структура ROS 2 компонентов;
* минимальное количество неявного поведения;
* удобство code review и сопровождения.

Стиль кода не должен быть причиной усложнения архитектуры или ухудшения читаемости.

---

## 2. Структура файлов

Для C++ используются:

* `.cpp` — исходные файлы;
* `.hpp` — заголовочные файлы.

Пример:

```text
include/
└── package_name/
    └── my_node.hpp

src/
└── my_node.cpp
```

Заголовочные файлы должны использовать:

```cpp
#pragma once
```

вместо include guards.

---

## 3. Структура ROS 2 package

Каждый ROS 2 package должен придерживаться единой структуры:

```text
src/
└── some_folder/
    └── pkg_name/
        ├── include/
        │   └── some_folder/
        │       └── pkg_name/
        │           └── *.hpp
        │
        ├── src/
        │   └── *.cpp
        │
        ├── test/
        │   ├── src/
        │   │   └── *_test.cpp
        │   ├── CMakeLists.txt
        │   └── main.cpp
        │
        ├── CMakeLists.txt
        └── package.xml
```

### `include/`

Содержит заголовочные файлы публичного API package.

Структура директорий внутри `include/` должна повторять namespace и имя package:

```text
include/
└── some_folder/
    └── pkg_name/
        └── device.hpp
```

Например:

```cpp
#include "some_folder/pkg_name/device.hpp"
```

### `src/`

Содержит реализации, соответствующие заголовочным файлам:

```text
src/
└── device.cpp
```

Для класса `Device`:

```text
include/some_folder/pkg_name/device.hpp
src/device.cpp
```

### `test/`

Все тесты package находятся в отдельной директории:

```text
test/
├── src/
│   ├── device_test.cpp
│   └── driver_test.cpp
├── CMakeLists.txt
└── main.cpp
```

Имена файлов тестов должны заканчиваться на:

```text
_test.cpp
```

Например:

```text
device_test.cpp
serial_driver_test.cpp
pressure_sensor_test.cpp
```

Тесты должны находиться отдельно от production code и не смешиваться с файлами из `src/`.

### `CMakeLists.txt`

Корневой `CMakeLists.txt` package отвечает за:

* описание package;
* поиск зависимостей;
* сборку library/executable;
* установку targets;
* подключение тестов.

### `package.xml`

`package.xml` содержит ROS 2 package metadata и зависимости.

Если package непосредственно использует другую ROS 2 package или библиотеку, зависимость должна быть явно указана.

### Namespace

Namespace C++ должен соответствовать структуре проекта.

Например:

```cpp
namespace some_folder::pkg_name
{
    // ...
}
```

Для ROS 2 package рекомендуется избегать глобального namespace для классов и функций проекта.

### Новые packages

При создании нового ROS 2 package необходимо сохранять эту структуру, даже если package пока содержит только несколько файлов.

Это обеспечивает единообразие проекта и упрощает:

* навигацию по коду;
* code review;
* подключение тестов;
* поддержку CMake;
* рефакторинг;
* работу новых разработчиков.

## 4. Форматирование

Для автоматического форматирования используется `clang-format`.

Конфигурация проекта находится в:

```text
.clang-format
```

Основные правила проекта:

* отступ — 4 пробела;
* максимальная длина строки — 100 символов;
* пробелы используются вместо tabs;
* фигурные скобки используются явно;
* форматирование должно быть единообразным во всём проекте.

Пример:

```cpp
void ServoDevice::publish_servo_control(const uint8_t control_signal)
{
    RCLCPP_DEBUG(
        node_->get_logger(),
        "Published control signal: %d",
        static_cast<int>(control_signal));
}
```

Не следует выполнять ручное форматирование, противоречащее `.clang-format`.

### Форматирование при сохранении

В VS Code рекомендуется включить автоматическое форматирование C++ при сохранении.

CI-проверка `clang-format` может быть отключена на отдельных этапах развития проекта, однако код должен соответствовать `.clang-format`.

## 5. Именование

### Файлы

Используется `snake_case`:

```text
servo_device.cpp
servo_device.hpp
serial_driver.cpp
```

### Классы

Используется `PascalCase`:

```cpp
class ServoDevice;
class SerialDriver;
class PressureSensor;
```

### Функции и методы

Используется `snake_case`:

```cpp
void publish_servo_control();
bool initialize_device();
```

### Переменные

Используется `snake_case`:

```cpp
uint8_t control_signal;
double pressure_value;
```

### Приватные поля

Приватные поля класса заканчиваются на `_`:

```cpp
class ServoDevice
{
private:
    rclcpp::Node::SharedPtr node_;
    uint8_t control_signal_;
};
```

### Константы

Константы проекта записываются в `UPPER_CASE`:

```cpp
constexpr int MAX_RETRIES = 3;
constexpr double MAX_PRESSURE = 10.0;
```

### Enum

Значения `enum` записываются в `UPPER_CASE`:

```cpp
enum class DeviceState
{
    DISCONNECTED,
    CONNECTING,
    CONNECTED
};
```

---

## 6. Классы

Класс должен иметь одну понятную ответственность.

Не следует создавать классы, которые одновременно:

* работают с аппаратным интерфейсом;
* обрабатывают ROS 2 сообщения;
* содержат бизнес-логику;
* управляют состоянием других компонентов.

Предпочтительно разделять ответственность:

```text
ROS 2 Node
    ↓
Device / Driver
    ↓
Hardware Interface
```

Например:

```cpp
class ServoDevice
{
public:
    void send_command(uint8_t command);

private:
    void handle_command(uint8_t command);

    SerialDriver serial_driver_;
};
```

---

## 7. Конструкторы

Конструкторы с одним аргументом должны использовать `explicit`, если не предполагается неявное преобразование.

Хорошо:

```cpp
explicit ServoDevice(rclcpp::Node::SharedPtr node);
```

Не следует допускать неявные преобразования без явной необходимости.

---

## 8. `const`

`const` должен использоваться там, где значение не изменяется.

Хорошо:

```cpp
void process_message(const Message& message);
```

Для методов, которые не изменяют состояние объекта, используется `const`:

```cpp
rclcpp::Logger get_logger() const;
```

Не следует убирать `const` только ради сокращения записи.

---

## 9. Указатели и ссылки

Для владения объектом используются smart pointers.

Предпочтительно:

```cpp
std::unique_ptr<Device> device_;
std::shared_ptr<Device> device_;
```

Raw pointers (`T*`) не должны использоваться для владения памятью.

Если функция не принимает владение объектом, предпочтительно использовать ссылку:

```cpp
void process_message(const Message& message);
```

---

## 10. ROS 2 Nodes

ROS 2 node должна иметь чёткую ответственность.

Node не должна превращаться в контейнер всей логики компонента.

Предпочтительная структура:

```text
Node
├── Parameters
├── Publishers
├── Subscribers
├── Services / Actions
└── Component logic
        ↓
    Device / Driver / Controller
```

ROS 2 API должен использоваться для взаимодействия между компонентами, а внутренняя логика по возможности должна быть отделена от ROS 2 интерфейсов.

---

## 11. Publishers и Subscribers

Имена ROS 2 интерфейсов должны соответствовать существующей структуре проекта.

При создании publisher/subscriber необходимо явно указывать QoS, если используется не стандартное поведение:

```cpp
publisher_ = node_->create_publisher<std_msgs::msg::UInt8>(
    "command",
    rclcpp::QoS(10));
```

Callback должен быть коротким и не содержать большое количество бизнес-логики.

Предпочтительно:

```cpp
void ServoDevice::command_callback(
    const std_msgs::msg::UInt8::ConstSharedPtr& msg)
{
    send_command(msg->data);
}
```

а не помещать всю обработку устройства непосредственно в callback.

---

## 12. Parameters

Конфигурационные значения, которые могут изменяться между запусками, должны быть ROS 2 parameters, а не hard-coded значениями.

Например:

```cpp
node_->declare_parameter<std::string>(
    "device_port",
    "/dev/ttyAMA2");
```

Не следует без необходимости делать аппаратные параметры частью исходного кода:

```cpp
// Не рекомендуется
const char* PORT = "/dev/ttyAMA2";
```

---

## 13. Логирование

Для логирования используется ROS 2 logging API:

```cpp
RCLCPP_INFO(node_->get_logger(), "Device initialized");
RCLCPP_WARN(node_->get_logger(), "Device timeout");
RCLCPP_ERROR(node_->get_logger(), "Failed to open device");
RCLCPP_DEBUG(node_->get_logger(), "Received command: %d", command);
```

Не следует использовать `std::cout` или `printf` для штатного логирования ROS 2 node.

Уровень логирования должен соответствовать ситуации:

* `DEBUG` — подробная отладочная информация;
* `INFO` — нормальные события;
* `WARN` — потенциальная проблема, не остановившая работу;
* `ERROR` — ошибка, влияющая на работу компонента;
* `FATAL` — критическая ошибка, после которой продолжение работы невозможно.

Не следует использовать `ERROR` для обычных диагностических сообщений.

---

## 14. Обработка ошибок

Ошибки должны обрабатываться явно.

Не следует игнорировать результат операций, которые могут завершиться ошибкой:

```cpp
// Плохо
device_->initialize();
```

Если результат важен:

```cpp
if (!device_->initialize()) {
    RCLCPP_ERROR(
        node_->get_logger(),
        "Failed to initialize device");
    return false;
}
```

Для аппаратных интерфейсов необходимо учитывать:

* timeout;
* потерю соединения;
* некорректные данные;
* недоступность устройства;
* повторное подключение;
* корректное завершение работы.

---

## 15. Аппаратные интерфейсы

Код работы с UART, I2C, CAN и другими аппаратными интерфейсами должен быть изолирован от ROS 2 логики настолько, насколько это возможно.

Предпочтительно:

```text
ROS 2 Node
    ↓
Device
    ↓
Driver
    ↓
Hardware
```

Например:

```text
ServoNode
    ↓
ServoDevice
    ↓
SerialDriver
    ↓
/dev/ttyAMA2
```

Node не должна самостоятельно содержать низкоуровневую работу с serial/I2C/CAN, если для этого существует отдельный driver/device слой.

---

## 16. Время и timestamps

При работе с сенсорами и ROS 2 messages необходимо корректно использовать timestamps.

Для сообщений, содержащих данные сенсоров, timestamp должен соответствовать времени получения или измерения данных согласно архитектуре конкретного компонента.

Не следует без необходимости использовать текущее время вместо timestamp, который уже содержится в исходных данных.

---

## 17. TF и `frame_id`

Для сообщений, связанных с пространственным положением или ориентацией, необходимо корректно указывать `frame_id`.

Имена frame должны соответствовать принятой в проекте TF-структуре.

Не следует создавать новые frame без необходимости.

Изменения TF tree должны быть явно указаны в Pull Request.

---

## 18. Magic numbers

Не следует использовать необъяснимые числовые значения:

```cpp
if (retry_count > 3)
{
    ...
}
```

Предпочтительно:

```cpp
constexpr int MAX_RETRIES = 3;

if (retry_count > MAX_RETRIES)
{
    ...
}
```

Для параметров, которые должны изменяться во время конфигурации системы, следует использовать ROS 2 parameters.

---

## 19. Комментарии

Комментарии должны объяснять **почему**, а не просто **что** делает код.

Плохо:

```cpp
// Increment counter
counter++;
```

Хорошо:

```cpp
// Allow three retries before reporting a communication failure.
retry_count++;
```

Не следует добавлять комментарии, которые просто повторяют код.

---

## 20. Header files

Заголовочные файлы должны содержать только необходимые объявления.

Не следует добавлять тяжёлые include без необходимости.

Предпочтительно использовать forward declarations там, где это возможно.

Например:

```cpp
namespace rclcpp
{
class Node;
}
```

вместо подключения полного заголовка, если он не требуется для объявления класса.

При этом читаемость имеет приоритет над чрезмерной оптимизацией include-зависимостей.

---

## 21. Include order

Include должны быть организованы последовательно.

Рекомендуемый порядок:

1. собственный header текущего `.cpp`;
2. заголовки проекта;
3. ROS 2;
4. сторонние библиотеки;
5. стандартная библиотека.

Пример:

```cpp
#include "servo_device/servo_device.hpp"

#include "serial_driver/serial_driver.hpp"

#include <rclcpp/rclcpp.hpp>
#include <std_msgs/msg/u_int8.hpp>

#include <cstdint>
#include <memory>
```

Собственный header текущего `.cpp` рекомендуется подключать первым. Это позволяет обнаружить проблемы с его самодостаточностью.

---

## 22. RAII

Ресурсы должны управляться через RAII, когда это возможно.

Предпочтительно использовать:

* `std::unique_ptr`;
* `std::shared_ptr`;
* контейнеры STL;
* классы-владельцы ресурсов.

Не следует вручную управлять памятью через `new` / `delete`, если для этого нет специальной причины.

---

## 23. CMake

Новые зависимости должны быть явно указаны в `CMakeLists.txt` и `package.xml`.

Не следует рассчитывать на транзитивные зависимости:

```cmake
find_package(rclcpp REQUIRED)
find_package(std_msgs REQUIRED)
```

Если код напрямую использует библиотеку или ROS 2 package, соответствующая зависимость должна быть объявлена явно.

---

## 24. Generated files и build artifacts

Следующие директории не должны добавляться в Git:

```text
build/
install/
log/
```

Также не следует коммитить:

* временные файлы;
* IDE-specific файлы;
* локальные логи;
* бинарные артефакты;
* файлы, генерируемые системой сборки.

Исключения должны быть явно обоснованы.

---

## 25. Code Review

При review необходимо обращать внимание не только на форматирование, но и на:

* архитектуру;
* читаемость;
* ответственность классов;
* обработку ошибок;
* ROS 2 interfaces;
* QoS;
* параметры;
* TF;
* timestamps;
* управление ресурсами;
* аппаратные ошибки;
* тестируемость;
* потенциальные регрессии.

Форматирование должно проверяться автоматически через `.clang-format`, когда соответствующая CI-проверка включена.

---

## 26. Что важнее всего

При написании нового кода необходимо придерживаться следующего порядка приоритетов:

1. **Корректность**
2. **Безопасность**
3. **Понятная архитектура**
4. **Надёжность**
5. **Тестируемость**
6. **Читаемость**
7. **Единообразие стиля**
8. **Оптимизация производительности**

Стиль кода не должен становиться причиной усложнения архитектуры.

Если существующий код нарушает эти правила, его не следует автоматически переписывать только ради соответствия стилю. Массовое форматирование и отдельные рефакторинги должны выполняться отдельными Pull Request.
